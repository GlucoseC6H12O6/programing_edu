# Programming Fundamentals 교육 사이트

[기획서](programming-fundamentals-education-site-plan.md)의 실행 시각화 엔진 구현.
**Python·JavaScript 트레이서가 모두 동작합니다.** 레슨의 코드는 손으로 만든
데이터가 아니라 AST를 계측해 **진짜 런타임으로 실행한** 결과입니다.

| | 계측기 | 빌드 타임 | 브라우저 |
|---|---|---|---|
| Python | [`tracer.py`](src/engine/python/tracer.py) (`ast`) | CPython | Pyodide |
| JavaScript | [`tracer.ts`](src/engine/javascript/tracer.ts) (acorn) | Node | Web Worker |

각 언어에서 **같은 파일**이 두 곳에서 돌아가므로 "미리 만든 트레이스"와 "직접
실행한 트레이스"가 갈라질 수 없고, 갈라지지 않았다는 것을 레슨 화면의 버튼으로
그 자리에서 확인할 수 있습니다.

```bash
npm install
npm run dev          # http://localhost:4321
npm run trace:emit   # 레슨 코드를 실행해 골든 트레이스 생성
npm run trace:check  # 커밋된 트레이스가 현재 실행 결과와 같은지 검증 (CI용)
npm run trace:show content/lessons/p08-conditionals/trace.golden.json  # 단계 문구 검수
npm run verify       # typecheck + trace:check + build
```

Python 3.10+ 와 Node 24+ 가 필요합니다. Python 인터프리터는 `PYTHON` 환경
변수로 지정할 수 있고, 스크립트는 Node의 타입 제거 실행(`--experimental-strip-types`)을
쓰므로 파라미터 프로퍼티 같은 *변환이 필요한* TypeScript 문법은 쓰지 않습니다.

## 핵심 아키텍처 결정

### 1. 실행과 재생을 분리한다 (record → replay)

Step / Prev / Auto / 타임라인 / 중단점까지 실행을 **라이브 디버거로 만들지
않는다.** 코드를 끝까지 한 번 실행하면서 이벤트 스트림을 기록하고, UI는 그
배열 위에서 커서만 움직인다.

```
소스 → [계측 + 실행] → 이벤트 배열 → [reducer] → 상태 → [UI]
                                        ↑
                                    커서 이동만
```

이 결정에서 나머지가 따라온다.

- `Prev`가 역실행이 아니라 인덱스 감소가 된다 (§3.3이 요구한 스냅샷 방식)
- 타임라인 스크럽, "회차 건너뛰기", "마지막 회차로 점프"가 전부 같은 연산
- **두 언어 모두 일시정지 가능한 인터프리터를 만들 이유가 사라진다**
- UI가 `(trace, cursor) → 화면`인 순수 함수라 테스트가 쉽다

대가는 실행 도중 상호작용(`input()`)을 받을 수 없다는 것인데, §3.10이 이미
가상 파일시스템·가상 데이터 로더를 규정했으므로 입력은 레슨이 미리 제공한다.

### 2. 인터프리터를 직접 만들지 않고 실제 런타임을 계측한다

| | 방식 | 이유 |
|---|---|---|
| Python ✅ | `ast.NodeTransformer`로 프로브 삽입 → 빌드는 CPython, 브라우저는 Pyodide | 예외 타입·부동소수점·LEGB·연산자 의미가 진짜여야 한다 (§14.1) |
| JavaScript ✅ | acorn 파싱 → AST 프로브 삽입 → astring으로 재생성 → 빌드는 Node, 브라우저는 Web Worker | 흉내 낸 엔진은 `0.1 + 0.2`, `"1" + 1`, `[] == false`에서 조용히 거짓을 가르친다. J21/J22의 마이크로태스크 순서는 더하다 |

계측은 의미를 바꾸지 않는다. 연산자는 원래 연산자를 그대로 호출하고
(Python은 `operator` 모듈, JS는 `(a, b) => a * b` 형태의 실제 연산), `and`/`or`와
`&&`/`||`/`??`는 람다로 감싸 단축 평가를 보존한다(§P05).

**실행 격리도 규칙이 아니라 구조다.** Python은 `__builtins__`를 화이트리스트로
교체한다. `open`과 `import`는 화이트리스트에 넣는 대신 **트레이스에 매인 것으로
바꿔 끼운다**. 진짜 파일과 진짜 모듈을 열면 안전 문제 이전에, P18이 요구하는
커서와 P20이 요구하는 "module frame에서 도는 최상위 코드"를 그릴 수 없다. JavaScript는 생성한 코드를 `with (프록시) { ... }` 안에서 돌려 모든 자유
식별자 조회를 가로챈다. 화이트리스트 밖은 그대로 `ReferenceError`가 된다.

```
fetch("https://example.com")  → ReferenceError: fetch is not defined
require("fs")                 → ReferenceError: require is not defined
process.env                   → ReferenceError: process is not defined
Date.now()                    → ReferenceError: Date is not defined
Math.random()                 → TypeError: Math.random is not a function
```

`Date`와 `Math.random`이 빠진 것은 실수가 아니다. 골든 트레이스는 매 빌드에서
같아야 검증이 성립하므로 **비결정적인 API는 애초에 닿을 수 없다.**

이벤트 수·실행 시간 상한이 있어 무한 루프는 `truncated`로 끝난다. 학습자 코드가
그 예외를 통째로 삼켜 버리는 경우까지 막으려고 브라우저 쪽은 Web Worker에서
돌리고 바깥에서 `terminate()`로 끊는다.

"의미를 바꾸지 않는다"는 주장이라 검사로 박아 뒀다. 빌드는 매번 레슨 코드를
**계측 없이 그대로도** 실행해 stdout을 대조한다. 계측이 프로그램을 조금이라도
바꾸면 화면의 모든 설명이 거짓이 되므로, 가장 싸고 확실한 방어선이다.

백엔드 러너는 채택하지 않는다. §3.10이 네트워크·실제 파일·패키지 설치를 모두
금지해서 백엔드가 줄 수 있는 것이 없고, 샌드박스 인프라와 왕복 지연만 남는다.

**줄 번호를 어떻게 지키는가는 언어마다 다르다.** Python은 삽입한 노드가 원본
노드의 위치를 물려받아 트레이스백 줄 번호가 학습자가 보는 줄과 그대로 일치한다.
JavaScript는 astring이 코드를 다시 찍어내므로 생성 코드의 줄 번호가 원본과
다르다. 대신 모든 프로브가 원본 위치를 인수로 들고 다니고, 오류 줄 번호는 직전
`line` 프로브가 기록한 위치를 쓴다. **문장 단위 정확도는 트레이스백과 같다.**

> **주의** — 계측 코드와 원본 소스의 위치 매핑을 처음부터 유지해야 한다.
> 어긋나면 현재 줄 하이라이트가 통째로 무너진다. 이벤트마다 `span`을 들고
> 다니는 것이 그 자리다.

### 3. 골든 트레이스를 커밋한다

레슨 기본 코드의 트레이스는 빌드 때 생성해 저장소에 커밋한다.

- 레슨 진입 시 Pyodide(~10MB) 다운로드 없이 **즉시** 단계 실행이 가능하다
- 학습자가 코드를 편집한 순간에만 실행기를 지연 로딩해 같은 코드로 재생성한다
- `npm run trace:check`를 CI에 걸면 §13.3의 "모든 Step 이벤트와 설명 문구가
  코드 실행 결과와 일치한다"가 사람 검수가 아니라 자동 검사가 된다

두 경로가 갈라지면 "미리 만든 설명"과 "직접 실행한 결과"가 다른 말을 하게 되므로,
레슨 화면의 **`브라우저에서 직접 실행`** 버튼이 그 자리에서 다시 실행해 커밋된
트레이스와 이벤트 단위로 비교한다. 비교하는 함수는 두 언어가 하나를 같이 쓴다
([`compare.ts`](src/engine/trace/compare.ts)의 `diffEvents`). 프로덕션 빌드를
띄워 확인한 결과는 아래와 같다.

| 레슨 | 이벤트 | 빌드 | 브라우저 | 결과 |
|---|---:|---|---|---|
| p08-conditionals | 34 | CPython | Pyodide | 완전 일치 |
| p11-nested-loops 3×3 | 142 | CPython | Pyodide | 완전 일치 |
| p11-nested-loops 9×9 | 1,174 | CPython | Pyodide | 완전 일치 |
| j08-loops counter | 26 | Node | Web Worker | 완전 일치 |
| j08-loops forof | 18 | Node | Web Worker | 완전 일치 |
| j08-loops break | 30 | Node | Web Worker | 완전 일치 |

실행기는 **누를 때만** 내려받는다. 레슨 페이지를 여는 것만으로는 아무것도 받지
않고, Python은 Pyodide(~10MB)를, JavaScript는 계측기 청크(~50KB)를 그때 가져온다.
JavaScript 쪽은 실행기가 이미 브라우저 안에 있으므로 런타임 다운로드가 아예 없다.

### 4. 단계 설명은 손으로 쓰지 않는다

P11을 9×9로 확장하면 단계가 436개다. §9.3의
`[실행 위치] + [실제 값] + [변경/선택] + [다음 흐름]`은 이벤트에서 기계적으로
생성할 수 있는 형태이므로 [`narrate.ts`](src/engine/trace/narrate.ts)가 만들고,
레슨은 특정 단계만 이벤트의 `message`로 덮어쓴다. §3.11의 스크린 리더 내레이션이
같은 자리에서 따라 나온다.

조사(은/는, 이/가, 으로/로)는 [`josa.ts`](src/engine/trace/josa.ts)가 계산한다.
값이 숫자나 영문 식별자로 끝나는 경우가 많아 한국어 독음의 받침까지 다룬다
(`1로`, `3으로`, `W01로`).

### 원고는 트랙마다 교재 파일 하나가 단일 출처다

두 트랙의 본문은 각각 `content/python-visible-textbook-p01-p24.md`와
`content/javascript-visible-textbook-j01-j23.md`에 전부 있다. 레슨 폴더의
`meta.yaml`에는 **기계가 쓰는 사실만** 둔다(단계, 선행 레슨, 예제 파일,
트레이스 목록). 본문 요약을 meta.yaml에도 적어 두면 반드시 어긋나기 때문이다.
예상 시간도 적지 않는다 — 원고 분량과 트레이스 길이에서 `estimate.ts`가
계산한다. 손으로 적은 숫자는 원고가 자라도 그대로 남는다.

교재의 **첫 레슨 이전** 글(목적, 권장 사용법, 시각 언어 표, 학습 지도)도
원고에서 그대로 온다. `/guide/python`·`/guide/javascript`가 그 자리다.

교재는 레슨마다 `## 1.`~`## 18.` 열여덟 개 절을 갖는다. 이 규칙이 깨지면
`textbook.ts`가 빌드를 세운다. 반쪽짜리 페이지가 조용히 나가는 것보다 낫다.

**두 트랙이 같은 열여덟 개 절을 쓴다.** 같은 자리에 같은 종류의 내용이 있어야
P09와 J08을 나란히 놓고 "여기서 두 언어가 갈린다"고 말할 수 있다. JavaScript
교재의 마지막에 그 대조표가 있다.

**플레이어가 돌리는 코드도 교재에서 나온다.** §8(실행 전 예측 문제)과
§13(업무형 예제)의 코드가 `code/predict.py`·`code/predict.js`,
`code/work.py`·`code/work.js`로 복사되고 트레이스는 거기서 만들어진다. 교재가
권하는 흐름이 "예측 → Step → 관찰"인데, 플레이어가 다른 코드를 돌리면 화면과
원고가 서로 다른 프로그램을 이야기하게 된다. `npm run textbook:check`가 둘이
어긋나면 빌드를 세운다.

### 픽스처의 역할이 바뀌었다

`mulDemo.ts`는 트레이서를 쓰기 전 **스키마를 검증하려고** 손으로 만든
트레이스였다. 이제 트레이서가 이벤트를 만들므로, 픽스처는 두 가지로 남는다.

1. **§16 단계표의 실행 가능한 명세** — 트레이서 출력과 이벤트 단위로 대조한다.
   `detail`이나 이벤트 순서를 건드리면 빌드가 즉시 실패한다.
2. **P11의 해설 오버레이** — 손으로 다듬은 문장을 얹는다. 구조가 완전히 같을
   때만 얹히므로, 어긋난 단계에 엉뚱한 설명이 붙는 일이 없다.

### 빌드가 검사하는 것

| 검사 | 무엇을 막는가 |
|---|---|
| 교재 §8·§13의 코드 vs 레슨 예제 파일 | 원고와 플레이어가 서로 다른 프로그램을 이야기하는 것 |
| 교재의 절 구성 (레슨마다 `1.`~`18.`) | 원고가 규칙을 벗어났는데 반쪽짜리 페이지가 나가는 것 |
| 계측 실행 vs 일반 실행의 stdout (`python3 file.py` / `node file.js`) | 계측이 프로그램의 의미를 바꾸는 것, JS는 출력 표기가 실제 `console.log`와 어긋나는 것까지 |
| 트레이서 출력 vs §16 명세(픽스처) | 대표 레슨의 단계 구성이 몰래 바뀌는 것 |
| 커밋된 골든 vs 지금 실행 결과 | 코드는 고쳤는데 트레이스를 다시 안 만드는 것 |
| 모든 스톱에서 설명 문구 생성 (물음표·빈 자리 금지) | 특정 이벤트에서 해설이 비거나 `?`가 그대로 나가는 것 |
| keyframe 점프 vs 순차 재생 | 타임라인·Prev가 조용히 틀린 상태를 보여주는 것 |
| 줄 번호가 그 이벤트가 속한 **파일**의 범위 안인지 | 여러 파일이 도는 트레이스(P20·J19)에서 하이라이트가 없는 줄을 가리키는 것 |
| 비동기 실행 순서 (계측 vs 진짜 node) | 트레이서의 microtask·타이머 큐가 진짜 이벤트 루프와 다른 순서로 도는 것 |
| 종료 시 프레임 수지, 힙 참조 유효성 | 프레임 누수(제너레이터·module 함수에서 실제로 잡혔다), 가리키는 대상이 없는 참조 |
| 브라우저 실행 vs 커밋된 골든 (수동, 두 언어 공통) | 빌드 경로와 실행 경로가 갈라지는 것. 같이 도는 파일(P20·J19)과 실행 전 디스크 내용(P18)까지 넘겨야 **같은 입력**이 된다 — 그러지 않으면 갈라진 것이 아니라 한쪽에 입력을 덜 준 것이 실패로 보인다 |

### 이벤트의 `detail` 규칙

`core`는 **의미 단위를 닫는 이벤트**에 붙인다(§3.2). 예를 들어 프레임 생성과
두 매개변수 바인딩은 §16 표에서 한 단계이므로, 앞의 둘은 `expression`이고
마지막 `PARAMETER_BIND`만 `core`다. 상세도를 낮춰도 상태는 항상 모든 이벤트를
적용해 계산하고 **멈추는 지점만** 걸러낸다. 숨기는 것과 실행하지 않는 것은 다르다.

## 현재 상태

**콘텐츠** — Python 트랙 P01~P24와 JavaScript 트랙 J01~J23, 총 47개 레슨이
각각 18개 절을 갖추고 **전부 단계 실행이 붙어 있다**(트레이스 94개, 5,646개
이벤트). 47개 모두 교재의 §8 예측 문제와 §13 업무형 예제를 그대로 돌린다.

**Python 트레이서가 다루는 문법** — 함수 정의/호출/반환(재귀 포함), `for`/`while`,
`break`/`continue`, `if`/`elif`/`else`, 대입·복합 대입·튜플 대입·`del`,
list/tuple/dict/set 리터럴과 첨자 읽기·쓰기, `append`/`pop`/`remove`,
산술·비교·단항 연산(값 치환 포함), `and`/`or`의 단축 평가, `print`,
`try`/`except`/`raise`, 그리고 잡히지 않은 예외의 호출 스택 전파.
여기에 이번에 더한 것 — `class`와 attribute 읽기/쓰기, method 호출,
`with`와 파일 읽기/쓰기, `import`(레슨이 함께 싣는 `.py`와 허용된 표준 모듈),
컴프리헨션 내부, `lambda` 호출, `yield`와 멈춘 프레임.

**JavaScript 트레이서가 다루는 문법** — 함수 선언/호출/반환(재귀 포함),
`let`/`const`/`var`와 구조 분해 대입(기본값 포함), 카운터 `for`·`for...of`·
`for...in`·`while`, `break`/`continue`, `if`/`else if`/`else`, 배열·객체 리터럴과
첨자·점 읽기·쓰기, `push`/`pop`/`shift`/`splice` 같은 변형 메서드,
산술·비교·단항 연산(값 치환 포함), `&&`/`||`/`??`의 단축 평가,
`console.log`/`warn`/`error`, `try`/`catch`/`finally`/`throw`, 그리고 잡히지 않은
예외의 호출 스택 전파. 여기에 이번에 더한 것 —

- **함수 값**: 화살표 함수와 함수 표현식의 몸통을 선언과 똑같이 계측한다.
  `arr.map(n => n * 2)`처럼 **빌트인이 부르는 콜백**도 프레임이 열리고 닫힌다.
  호출식이 사용자 코드에 없으므로 지날 프로브도 없다는 사실 자체가 J12의
  내용이라, 그 경우 몸통의 `enter`가 호출 이벤트를 대신 만들고 프레임 정리도
  몸통의 `finally`가 맡는다. 프레임 카드에는 `map 콜백#1`처럼 **넘겨받은 쪽의
  이름**이 붙는다.
- **class**: 설계도 카드(초기 상태 규칙 + 공유 method)와 instance 카드를 따로
  그린다. `new`는 빈 카드를 만든 뒤 constructor가 칸을 하나씩 붙이는 순서로
  보인다.
- **module**: `import`/`export`를 계측해 의존 파일의 최상위 코드가 자기
  프레임에서 먼저 도는 장면을 만든다. 이벤트마다 파일 경로를 들고 다니므로
  코드 패널이 실행 중인 파일로 바뀐다.
- **비동기**: `Promise`, `async`/`await`, `setTimeout`. 아래 별도 항목 참고.

**아직 안 다루는 것** — Python: 데코레이터, 클로저 스코프의 세밀한 표현.
JavaScript: `switch`, `do...while`, 제너레이터, `import`의 이름 바꾸기(`as`),
`export default`, 그리고 **블록 Scope**. 마지막 것은 프레임 단위로만 이름을
추적하기 때문이다 — `if` 블록 안에서 같은 이름을 다시 선언하면 실행은
정상이지만 Memory 카드는 바깥 것을 덮어쓴 것처럼 보인다. 그래서 J11의 §8은
shadowing을 **함수 경계**로 보여 준다. 화면이 사실대로 그릴 수 있는 프로그램만
돌린다는 원칙이 여기서도 같다.

**언어마다 다르게 보이는 것** — 카운터 `for`와 `while`은 다음 값을 미리 알 수
없다. Python의 `for i in range(3)`이 `[0, 1, 2]` 트랙을 그리는 자리에서
JavaScript의 `for (let i = 0; i < 3; i++)`은 회차마다 조건 검사가 그대로
드러난다. 이건 트레이서의 한계가 아니라 두 언어의 실제 차이이므로 그대로 보여
준다 (§9.2 8번 "언어 비교"의 재료).

**비동기를 결정적으로 돌린다** — J21~J23은 진짜 타이머와 진짜 microtask 큐로는
성립하지 않는다. 트레이스가 실행할 때마다 달라질 수 있고, 무엇보다 `traceSource`가
동기 함수라 프로그램이 끝나기 전에 돌아와 버려 비동기 부분이 통째로 빠진다.

그래서 트레이서가 **큐를 직접 든다**. `Promise`는 이 스케줄러 위에서 도는 작은
구현으로 바꾸고, `setTimeout`은 가상 시계에 예약하며, `async` 함수는 계측 단계에서
generator로 바꿔(`await` → `yield`) 드라이버가 한 걸음씩 민다. 동기 코드가 끝난
뒤 microtask를 전부 비우고 가장 이른 타이머 하나를 돌리는 순서까지 진짜 엔진과
같다.

이 주장이 맞는지는 매 빌드가 검사한다. 계측 실행의 stdout과 **진짜 node로 그냥
돌린** stdout을 대조하기 때문에, 순서가 한 줄이라도 어긋나면 빌드가 선다.

`await`에서는 프레임이 호출 스택을 떠났다가 돌아온다. 화면에서는 사라지지 않고
점선으로 남아 지역 변수를 그대로 들고 있다. Call Stack이 비었는데 프로그램이
끝나지 않은 순간을 설명하려고 STATE 패널에 **대기 중인 작업** 목록을 따로 둔다.

**엔진** — 이벤트 스키마 전체 정의, 동기 실행 이벤트의 리듀서, keyframe seek,
3열/반응형 레이아웃, 코드·반복 트랙·격자·호출 흐름·Call Stack·바인딩 전후 비교·힙 객체 내용,

애니메이션 감소 모드, 레슨 페이지(§9.2의 1·2·3·4·5·10번 블록).

## 원고가 요구한 것

레슨을 먼저 쓰고 나서 엔진의 다음 할 일을 정했다. 순서를 뒤집기 전에는 무엇을
만들지 짐작으로 골랐고, 짐작은 두 번 다 빗나갔다. 아래 목록은 전부 **P01~P24를
실제로 쓰다가 부딪힌 것**이다.

### 원고를 쓰다가 고친 것

| 발견 | 문제 | 조치 |
|---|---|---|
| P07 Set | 파이썬은 프로세스마다 문자열 해시를 무작위화한다. `set`의 순회 순서가 실행마다 달라져 골든 트레이스가 **매 실행 다른 파일**이 됐다. 8번 중 4번꼴로 `trace:check`가 깨지고, 브라우저 대조도 같은 확률로 어긋난다. | 트레이서가 set의 표시 순서를 `repr` 기준으로 고정하고 `unordered: true`를 붙인다. JS의 `Set`은 삽입 순서를 지키므로 정렬하지 않는다 — 이건 두 언어의 실제 차이다. |
| P07 Dictionary | 없던 키에 값을 넣는데 `` `retested` 위치가 ?에서 True로 바뀝니다``라고 설명했다. 삽입을 변경으로 취급한 것이다. | `narrate.ts`가 이전 값이 없으면 "자리가 새로 만들어지고 …가 들어갑니다"로 말한다. |

첫 번째는 특히 위험했다. 코드를 아무리 들여다봐도 안 나오고, CI가 절반만
실패하는 종류라 원인을 찾기도 어렵다. **`print(set)`은 레슨 코드에서 쓰지

### 원고가 요구해서 만든 것

원고를 먼저 쓴 덕에 "무엇을 만들어야 하는가"를 짐작하지 않았다. 아래 다섯은
전부 교재의 §9(단계 실행 Walkthrough)와 §10(Visual Script)이 요구한 것이고,
만든 뒤에는 그 절과 한 줄씩 대조해 확인했다.

| 무엇 | 원고의 요구 | 만든 것 |
|---|---|---|
| **클래스** (P21) | §10-1 "Class Card에는 초기화 규칙과 method를, Heap에는 instance 카드를 따로 둔다" · §10-2 "빈 instance를 만든 뒤 `__init__` frame을 push한다" | `__build_class__` 허용. `CLASS_DEFINE`·`INSTANCE_CREATE`·`ATTR_READ`/`ATTR_WRITE`. 생성은 `__new__`와 `__init__`을 **나눠 불러** 원고의 순서를 그대로 낸다. 설계도 카드와 인스턴스 카드가 따로 그려지고, `ATTR_READ`는 이름을 인스턴스에서 찾았는지 클래스에서 찾았는지(`owner`)를 남긴다. |
| **파일** (P18) | §5 "Disk file → File object(cursor+mode) → Python memory" · §10-1 "서로 다른 패널로 둔다" | 가상 파일 시스템. `open`은 화이트리스트가 아니라 **이 트레이스에 매인 통로**라서 커서와 내용을 화면에 그릴 수 있다. `FILE_OPEN`/`WRITE`/`READ`/`CLOSE`와 FILES 패널. `w` 모드가 기존 내용을 버리는 순간(§10-5의 "위험 사건")이 이벤트로 남는다. |
| **모듈** (P20) | §5 "두 파일을 나란히 둔다" · §10-2 "하이라이트를 imported module의 첫 줄로 옮긴다" · §10-6 "재import는 Import Cache에서" | 트레이스가 **여러 소스 파일**을 싣는다. import한 모듈은 자기 프레임에서 최상위 코드가 돌고, 코드 패널의 하이라이트가 그 파일로 넘어간다. 두 번째 import는 `cached: true`로 캐시 경로를 보여 준다. 표준 모듈은 결정적인 것만 연다(`json`·`math`·`statistics`·`csv`·`pathlib`). |
| **컴프리헨션** (P15) | §9의 4단계 (`n=1` 거짓 → `n=2` 참 → 12 → …) · §9의 "hidden result builder" | 컴프리헨션의 숨은 반복을 계측한다. 회차·필터 판정·결과 표현식이 각각 이벤트가 되고, 쌓이는 중인 결과가 `builder@n` 카드로 보인다. 필터에 걸린 원소는 결과 표현식으로 가지 않는 것이 그대로 드러난다. |
| **제너레이터·람다** (P23·P17) | P23 §8 "값을 요구할 때 비로소 시작한다" · P17 §9 "lambda frame은 호출마다 잠깐 생긴다" | generator 함수는 호출해도 몸통이 돌지 않고, `yield`에서 프레임이 `paused`로 남는다. `all(checks())`처럼 끝까지 소비하지 않은 프레임은 프로그램 종료 시 `reason: "abandoned"`로 정리된다. `key=lambda`는 호출마다 프레임을 만들어 무엇을 돌려줬는지 보여 준다. |

**교재가 찾아낸 버그.** 이 작업에서 코드를 읽어서 찾은 것은 하나도 없다.
전부 원고의 코드를 돌려 보다가 나왔다.

- `for index, (name, value) in enumerate(zip(...))` → `NameError: name '_' is not defined`.
  대상에서 이름을 뽑는 함수가 한 겹만 보고 `None`을 돌려줬고, 호출부가 그 자리를
  `["_"]`로 메워 **존재하지 않는 이름을 읽는 코드**를 만들고 있었다.
- module의 함수(`measurement_utils.parse_value`)를 부르면 프레임이 열린 채 남았다.
  호출부가 프레임을 열지 않는데 몸통의 `enter` 프로브는 돌기 때문이다.
  자체 검사의 "프레임 수지"가 잡았다.
- 파일 반복(`for line in file`)의 읽기가 직전 문장의 줄 번호에 붙었다.
- generator 함수는 호출해도 몸통이 돌지 않는다는 사실을 `call()`이 모르고 있었다.
  프레임 하나가 열린 채 남고, 그 뒤의 모든 이벤트가 엉뚱한 프레임에 기록됐다.

### JavaScript 원고가 요구해서 만든 것

J01~J23을 쓰면서 같은 일이 반복됐다. 원고가 "화면에서 이것이 보여야 한다"고
적으면 엔진에 그것이 없었다.

| 무엇 | 원고의 요구 | 만든 것 |
|---|---|---|
| **함수 값** (J10·J12~J14) | J12 §5 "우리 코드에는 호출식이 없다. 부르는 것은 `map`이다" · J10 §10 "함수 카드를 값과 똑같이 그린다" | 화살표 함수와 함수 표현식의 몸통을 선언과 같은 모양으로 계측한다. 호출부 프로브를 지나지 않은 호출은 몸통의 `enter`가 호출 이벤트를 대신 만들고, 프레임 정리는 몸통의 `try/finally`가 맡는다. 프레임 이름은 넘겨받은 쪽에서 딴다(`map 콜백#1`). |
| **점으로 읽고 쓰는 속성** (J06) | J06 §5 "Object는 이름표가 붙은 칸의 묶음" · §9 "그 상자를 가리키는 이름이 둘" | `row.value`와 `row.value = …`를 `ITEM_READ`/`ITEM_WRITE`로 낸다. 배열의 `length`나 문자열 method까지 읽기 사건으로 그리면 화면이 의미 없는 줄로 덮이므로, 칸으로 그려지는 object일 때만 낸다. |
| **구조 분해** (J15) | J15 §9 "한 줄이 세 개의 이름을 만든다" | 패턴 안의 기본값·rest까지 이름으로 세고, 매개변수 자리의 구조 분해도 프레임에 각각의 카드를 만든다. 그 전에는 `function label({ id })`가 계측 코드에서 문법 오류를 냈다. |
| **class** (J20) | J20 §5 "설계도 카드와 실물 카드는 다른 것" · §9 "카드가 비어서 생기고 칸이 하나씩 붙는다" | `CLASS_DEFINE`으로 설계도 카드를(초기 상태 규칙 + 공유 method), `new`는 `construct` 프로브로 프레임을 열고 `INSTANCE_CREATE`로 실물과 설계도를 잇는다. `first.judge === second.judge`가 `true`인 이유가 그림에 있다. |
| **module** (J19) | J19 §5 "import 줄에서 실행 위치가 건너간다" · §10-1 "지금 실행 중인 파일 이름을 크게" | `import`/`export`를 계측해 의존 파일을 자기 프레임에서 돌린다. 정적 정보 표를 파일들이 공유하고, 이벤트마다 파일 경로를 들고 다녀 코드 패널이 따라 바뀐다. |
| **비동기** (J21~J23) | J21 §10-5 "동기 코드가 끝나 Call Stack이 비는 순간을 명시한다" · J22 §10-1 "프레임이 사라지지 않고 옮겨 간다" | 결정적 스케줄러와 그 위에서 도는 `Promise`. `async` 함수는 계측 단계에서 generator가 되고(`await` → `yield`) 드라이버가 민다. `AWAIT_SUSPEND`에서 프레임이 스택을 떠나고 `AWAIT_RESUME`에서 돌아온다. STATE 패널의 **대기 중인 작업** 목록이 "스택은 비었는데 프로그램은 안 끝났다"를 설명한다. |

**JavaScript 교재가 찾아낸 버그.** 여기서도 코드를 읽어서 찾은 것은 없다.

- `stats.add(3)` — 사용자 object의 method 이름이 `Set.add`와 겹쳐 컬렉션 변경
  이벤트가 잘못 나왔다. 진짜 배열·Set·Map일 때만 그 사건으로 그린다.
- `try` 블록을 지나는 예외의 줄 번호가 **try 문이 적힌 줄**로 기록됐다.
  실패한 줄이어야 한다.
- `return function check(...)`처럼 선언이 아닌 자리에서 만들어진 함수는 힙
  카드가 없어, 자체 검사가 "가리키는 대상이 없는 참조"로 잡았다.
- 설명 문구 검사가 JavaScript의 `undefined`를 "값을 못 찾은 빈 자리"로 오인해
  빌드를 세웠다. Python에서는 맞는 규칙이지만 JavaScript에서는 값 그 자체다.
- `typeof 선언되지_않은_이름`이 안전 스코프의 프록시에서 `ReferenceError`가 된다.
  진짜 엔진과 다르므로 그 문법을 §8에 쓰지 않고, 대신 "이름이 없다"를 오류로
  보여 주도록 원고를 고쳤다.

### 아직 없는 것

| 무엇 | 왜 |
|---|---|
| Python의 `any`/`all`이 콜백을 부르는 지점 | 빌트인 안에서 일어나는 일이라 AST로 닿지 않는다. `key=lambda`는 람다 자체를 감싸서 열었다. JavaScript 쪽은 **함수 몸통을 계측하고 몸통이 프레임을 정리하게** 바꿔 `map`·`filter`의 콜백이 보인다 — 같은 방식이 `tracer.py`에도 적용된다. |
| 중첩 컴프리헨션의 안쪽 `for` | 가장 바깥 하나만 계측한다. 생성 코드가 원래 의미와 어긋날 위험이 커지는데, 교재 §10-6이 중첩은 P11 격자로 넘긴다. |
| 상속과 `super()` | 교재 §6이 언급만 하고 §8·§13에 쓰지 않는다. 원고가 요구하지 않은 것은 만들지 않는다. |
| `dataclass`·데코레이터 | 위와 같다. §6의 참고 문단에만 있다. |

### 다음 단계

1. **§9.2 8번 "언어 비교" 블록** — 두 트랙이 같은 18개 절을 갖췄으므로 이제
   P09와 J08을 한 화면에 나란히 놓고 단계 수를 비교할 수 있다. 재료가 다 있는
   유일한 남은 블록이다.
2. **§3.8 인터랙션 패턴과 §9.2의 남은 블록** — 47개 레슨이 있으므로 "어떤
   레슨에서 무엇을 묻는가"를 이제 원고에서 뽑을 수 있다.
3. **Python 쪽 빌트인 콜백 계측** — JavaScript는 이번에 함수 값을 계측하면서
   `map`·`filter`의 콜백 프레임이 보이게 됐다. Python의 `any`·`all`이 몇 번째에서
   멈췄는지는 아직 안 보인다. 같은 방식(몸통 계측 + 몸통이 프레임을 정리)이
   `tracer.py`에도 적용된다.
4. **블록 Scope** — 리듀서의 프레임에 블록 층을 하나 더 두면 J11의 §8을 블록
   shadowing으로 바꿀 수 있다. 지금은 화면이 사실대로 그릴 수 있는 범위에서
   함수 경계로 가르치고 있다.

### 보류한 것: 두 언어 트레이스의 구조 비교

`compare.ts`가 **같은 언어의 두 실행 경로**(빌드 ↔ 브라우저)를 대조하는 데는
그대로 쓰인다. 이건 정확 일치라 판정이 명확하다.

**언어를 가로지르는** 구조 비교는 만들지 않았다. 같은 일을 하는 Python 코드와
JavaScript 코드는 `let status;`처럼 한쪽에만 필요한 선언 때문에 이벤트 수가
어긋나고, 그 어긋남을 흡수하려면 "앞의 두 개는 건너뛴다" 같은 보정값이 붙는다.
보정값이 붙는 순간 검사는 무엇도 보증하지 못한다. §9.2 8번 블록은 자동 대조가
아니라 **레슨이 직접 고른 두 코드를 나란히 재생하는** 형태로 만드는 편이 맞다.
그때 필요한 것은 비교 알고리즘이 아니라 두 플레이어를 묶는 화면이다.
